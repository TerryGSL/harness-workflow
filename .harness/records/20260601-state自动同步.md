# 20260601-state自动同步
Type: feature

## What（解决什么 + 验收）
治用户痛点:每轮 state.json 全 null、架构文档不同步——因为它们是 advisory(靠"记得做")。
机械根治能机械化的部分:让 record.sh 生命周期自动写 state.json，不靠记得；并补回架构文档(README)。
验收:record.sh start 后 state.currentTask/taskType/currentStage 被自动写；done 后 currentStage=done；
README 反映风险分级 + state 自动同步；全测试绿。

## Decisions（非显然取舍）
- state 同步**走 state.sh 唯一入口**(不在 record.sh 里直接写 json)：保持"state.json 只有一个读写入口"的约束。
- 同步**失败不阻断** record 操作:state 是可删缓存，宁可它偶尔不准也不能因写 state 失败卡住沉淀。
- **不强求 README 机械同步**:无法机械验证"文档是否反映最新功能"，README 仍是 best-effort；但 state 这种结构化状态可以机械化，就机械化。区分"能机械化的"和"本质 advisory 的"，只攻前者。
- 架构文档(README)这轮**手动补**,并入本 feature(都属"补全沉淀完整性"),不算混功能。
- codex 审提两点"要改"经核实均为信息不全的 false positive(README 描述的风险分级确在同分支 c4e8e4d;done 校验全 `|| exit 1` 硬退出在 sync 之前)。不盲从,但采纳其方法论——加测试 done_fail_no_advance 把"done 失败不推进 state"从"我说不会"变成机械保证。
